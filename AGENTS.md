# amble-home

**Amaran BLE for ESPHome.** An ESPHome-native bridge that puts amaran (Aputure) BLE-mesh studio lights into Home Assistant as first-class devices: flash from a browser, join your Wi-Fi, import your fixtures from your amaran account or the amaran app's database, and the lights appear in HA. Nothing else.

**Ownership model, stated plainly:** Chris Williams owns the repo, the hardware, the decisions and the merge button. Claude writes and maintains all of the software. Chris does not read the code and does not intend to; he reads this file, the specs, the decisions and the issues. Write for that reader. Every artifact that asks Chris for a decision must be understandable without opening a source file.

- `docs/decisions.md`: durable rationale. Check it before questioning why something is the way it is.

- `docs/superpowers/specs/`: designs. Nothing in a spec is built until Chris approves it and the approval is recorded on its issue.
- `docs/fixtures.md`: the fixture support matrix, generated by `tools/fixture-matrix.py` from the amaran app's own tables; tested rows are edited in the script, never in the file.
- `docs/bench.md`: how a dev board and a Mac get along (first flash, USB logging trap, secrets). Procedure, rewritten in place.
- `docs/origin.md`: what this project inherits from the author's earlier studio bridge and the facts learned there. Read it before touching the mesh layer.
- The [wiki](https://github.com/clwill/amble-home/wiki): the documentation for people who *use* amble-home (installing, boards, lights, importing, Home Assistant, updating, troubleshooting). The files above are for people who *work on* it. A change in behavior that a user would notice updates the wiki page in the same slice.
- GitHub issues on `clwill/amble-home`: the work record. Pending work is an open issue; a decision with a revisit trigger is an issue created closed with the `decision` label.
- `CLAUDE.md` is the exact one-line shim `@AGENTS.md`. `CODEX.md` is a short handoff for Codex sessions.

## Standing rules

1. **The production box is production.** The author's studio is driven through Home Assistant by a production box running the release image. It is never flashed except as a deliberate update through the same path a stranger uses, after the dev board has run that build. amble-home development happens on a dedicated dev board against a spare fixture that is not on the production box. The dev build never sends group-address or broadcast mesh commands (`0xC000`, `0xFFFF`): those reach every fixture on the mesh, including production.
2. **Keys never enter the repo.** Mesh network and app keys, fixture MACs and anything derived from a user's `amaran.db` or amaran account are user data. They live on the device (NVS) and in the user's browser during import, never in YAML we ship, never in a log line, never in anything that ships to strangers (firmware, tools, this repo): logs and tool output say "fixture N". This repository is public, so the author's own fixture names, mesh addresses and box names stay out of its issues and docs as well; a bug report that needs them is handled with the reporter in private. `.gitignore` enforces the obvious cases; judgment covers the rest.
3. **The amaran app is the source of truth for the mesh.** We never provision fixtures, never manage mesh membership, never offer a fixture add/remove UI — with one explicit, deferred exception: the **take-over** door (a later milestone, tracked as an open idea) re-provisions fixtures into the box's own mesh for users who have neither cloud nor database access. It is opt-in and destructive, stays non-operational in the UI until a separate provisioning design is proven on the bench, and is never a routine path. Otherwise, users change fixtures in the amaran app and re-run the import.
4. **ESPHome owns everything ESPHome already does.** Wi-Fi, captive portal, Improv, OTA, the native HA API, logging, the web server. amble-home adds one external component (the mesh bridge) and a web flasher/importer page. If a problem looks like it needs a Wi-Fi reconnect loop, an MQTT client or a watchdog, the answer is an ESPHome component, not new code.
5. **Hardware evidence or it did not happen.** A change to the mesh layer is verified on the dev board with a fixture responding, and the evidence (log excerpt, HA state read-back) goes on the issue. Build-passes is not evidence.
6. **Chris decides scope; Claude decides implementation.** Platform, language, libraries and structure are Claude's calls, recorded in `docs/decisions.md` with alternatives rejected. Features, priorities, the stranger story and anything that costs money or touches production are Chris's.

## Working agreement (Codex + Claude)

The same model the author uses across his repositories, so he moves between them without relearning the process. The procedure lives in the `review-work-package` skill here.

- **One driver, one writer.** One named driver per issue. Parallel writers use separate worktrees.
- **The push is a gate.** Inspect the full diff and run verification proportional to the change (`verify-surfaces`) before any push. No review verdict authorizes a push, a release, or a flash of the production box.
- **Routine review is the default and needs no approval.** Every substantive code-bearing slice gets a fresh, read-only same-vendor review of a committed `base..head` range before the push gate. Docs, copy and mechanical edits are exempt.
- **Cross-model review is recommended, resolved once per issue,** when a slice touches: the mesh encryption or key-handling path; anything that persists or transmits user keys; the import page (it reads a key-bearing database in the user's browser); the OTA or partition layout; the release pipeline; the production cutover plan; an architecture decision; or unresolved correctness or scope ambiguity. The driver runs it through the Codex CLI bridge by default (standing authorization, bills the Codex plan); Chris may pick the GitHub handoff or a waiver per issue.
- **Review is explicit and read-only.** No hook, schedule or idle trigger starts a review. Reviewers never edit, commit, push or file issues.
- **`unattended`** on an issue means decision-complete and pre-authorized to run without Chris, within the ceiling his comment states. Chris applies it, or Claude applies it on Chris's explicit in-session say-so, quoting him in the ceiling comment. Never self-waive, never infer it.

**Contributions from others** are welcome as issues and pull requests. A pull request gets the same review as any other slice, and a change to the mesh layer still needs hardware evidence (a fixture responding) before it merges; say which board and which fixture.

## Status

**v1.0.0 released; the author's studio runs on amble-home.** Nine fixtures, six scenes, a group and a dashboard in Home Assistant, on one ESP32-S3 flashed from the flasher page with the release image, joined to Wi-Fi over Improv, with the fixtures imported through the account door. A rename in the amaran app reaches HA by a refresh and a Save. Every box is `amble-home-xxxxxx` (the last six digits of its hardware address) and its own mesh node at an address seeded at first boot; `amble-home.local` is an alias any box answers. CI builds one S3 image (8 MB, no PSRAM, for every S3 board) and one C6 image; the flasher page picks by chip; five boards have run the whole stranger path (`docs/fixtures.md` and the wiki's Boards page carry the matrices). The Edit page opens as a choice page (your amaran account, the app's database, take-over grayed as coming); the box makes amaran's sign-in call and hands the page a one-time token, the browser fetches the mesh; the password is used once and not stored unless the person checks *Remember*; the box never signs in on its own; rows say what changed since the last Save. Production takes new images over ESPHome's OTA from a release after the dev board has run it (`docs/decisions.md`, 2026-10-29). Releases reach boxes through the update feed (`amble-home.update.yaml`: Home Assistant shows an Update row with Install; the bench config leaves the feed out). Open ideas, each an issue: the take-over door, ID before Save on candidate keys, failure injection for the bench, a link from the HA device page to the box's pages (needs an ESPHome change), and the upstream ask for a public API to register a component at runtime. Bench procedure: `docs/bench.md`.
